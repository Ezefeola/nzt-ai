# Sizing the work

The size decides how much process the work carries. Size it by what the work involves and
how much it is worth to the person, never by how the request was phrased.

| Size | When | What it carries |
|---|---|---|
| **direct** | One result, small, its done criterion fits in one line, and redoing it would be cheap | One unit with `nzt-do`. No plan, no state file |
| **planned** | A few results that depend on each other, or something that is costly to redo, but it fits one plan approved once | A short plan (`nzt-plan`), `Plan/state.md` |
| **sliced** | Many results, an unclear path, or work that will span several sessions | A plan cut into units, each with its own stop (`nzt-plan`), `Plan/state.md` |

## Rules

- **In doubt, the lighter size.** When the work outgrows it, say so and propose the next.
- **The person can change the size at any moment**; record the change in *Decisions*.
- **Size cuts ceremony, never quality:** every size agrees its done criterion, verifies
  against it and ends with a verdict.
- **Fixed time is an option of any size:** when the person has a deadline, the deadline
  stays and scope is cut. The plan marks what is cuttable from the start.

## Examples

| Request | Size |
|---|---|
| Fix the spelling of this paragraph | direct |
| Organize a birthday: invitation, guest list, menu | planned |
| Write a ten-lesson course | sliced |
| A bug in a function | direct |
| Move house next month | sliced, done mostly by the person |
