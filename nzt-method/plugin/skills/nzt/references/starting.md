# Clarifying a request

A vague request cannot be sized or verified. Clarify it before anything else, with the
fewest questions that make it describable in one sentence.

## The starting questions

The default for any domain. A package in use may add its own; these still apply.

| Question | Why it matters |
|---|---|
| What should exist or change when this is over? | It is the work itself |
| For whom, and what will they do with it? | It decides form, depth and tone |
| By when, and how much is it worth to the person? | It decides the size and whether time is fixed |
| What already exists? | Earlier work, files, decisions, constraints already taken |
| What limits apply: money, time, rules, tools? | They cut options before proposing any |
| How will we know it went well? | It becomes the done criterion |

## How to ask

- **Deduce first.** Read the request, the folder, the state and the glossary; ask only what
  is left.
- **Ask everything left at once**, in a single message, never one question per turn.
- **Propose exploring instead** when the person does not know yet what they want (an idea,
  a creative search): a short round of options or research whose only output is a clearer
  request. Exploring is direct work done by `nzt-do`.
