LOS FRENOS SON UNA FEATURE

Autonomía no significa
movimiento perpetuo.

Por defecto, cada unidad termina en un borde revisable. El usuario puede autorizar un lote, pero los frenos materiales siguen existiendo.

QUÉ NO HACE

NZT no decide por vos.

No limita el conocimiento del modelo, no garantiza acierto perfecto, no usa MCP ni subagentes y no reemplaza el criterio técnico o de negocio.

NZT=cómo trabajar≠qué decidir

CABINA DE DEMO

Copiar, ejecutar, observar.

OBJETIVO25:00
01 · INICIO

Quiero crear desde cero “Radar”, un tablero web para registrar el estado verde, amarillo o rojo de cada integrante.

02 · APROBACIÓN

Apruebo el plan. Mantené modo acompañado y frená al terminar cada unidad.

03 · DEFINICIÓN FUNCIONAL

Este es el requerimiento completo y no hay nada más: no agregues reglas, pantallas ni capacidades que no estén acá; lo que no esté escrito queda fuera de alcance. Sin login: el equipo son siempre las mismas tres personas, Ana, María y Arnold, que ya están cargadas al iniciar; no se agregan ni se quitan. Cualquiera puede registrar o cambiar el estado de cualquiera de las tres, sin importar quién sea. Amarillo y rojo requieren una nota de 1 a 140 caracteres; en verde la nota es opcional. Cada persona tiene un único estado vigente y uno nuevo reemplaza al anterior, sin historial. Mostrar primero rojo, después amarillo, después verde y al final quienes todavía no tienen estado; dentro de cada grupo, por nombre. La pantalla cubre carga, error y vacío (nadie registró todavía). El tablero muestra el cambio apenas se guarda; otra pestaña lo ve al recargar. Los estados no se conservan: al reiniciar la aplicación, las tres vuelven sin estado.

04 · ARQUITECTURA

Estas son todas las decisiones técnicas; no agregues nada más, tiene que ser una aplicación mínima. Dos componentes separados, ambos en .NET 10: una API ASP.NET Core y un front Blazor Web App con render interactivo en servidor. API: vertical slice, minimal APIs, dominio anémico, EF Core directo con el proveedor en memoria y data seeding de Ana, María y Arnold al iniciar (sin base de datos ni migraciones) y Result convertido a HTTP con extensiones. Front: vertical slice, componentes inline, MudBlazor como librería de componentes; llama a la API con un cliente HTTP tipado cuya URL base apunta a la API local. Tests: unitarios con xUnit para las reglas de negocio; sin integración, sin test-first y sin end-to-end. Sin autenticación, Docker ni paquetes extra: se levanta en local con un dotnet run por proyecto.

05 · BUILD

Implementá todo.

06 · VERIFICACIÓN

Diseñá la verificación de la historia principal. Quiero probar la API y la pantalla. Mostrame primero el plan de pruebas, los datos necesarios y qué podés conducir desde esta sesión. No ejecutes hasta que lo apruebe.

Mirar:skill elegidaarchivo de estadostop realevidencia ≠ opinión
25 min en ventana externa. El guion completo está en presentation/demo/prompts.md. No intentes ejecutar todas las fases si el modelo tarda: mostrales el estado y saltá al checkpoint siguiente. El segundo prompt va recién cuando todos vieron el plan con approved: false; el cuarto, cuando arranque la unidad de arquitectura. El sexto debe producir un plan de pruebas y esperar; aprobarlo recién cuando todos hayan visto el freno.
