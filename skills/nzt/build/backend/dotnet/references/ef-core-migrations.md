# EF Core migrations

A migration records **one schema or data change**. A model change usually needs one; an agreed
data transformation or a database object outside the EF model can need one without the model
changing. **No migration is created without a concrete operation to perform.**

Load `nzt-build-backend-dotnet` and `nzt-build-backend-dotnet-ef-core` before applying this.

## It is generated by command, never written

**Every migration starts with `dotnet ef migrations add <Name>`. None is written from scratch**
— including when the command fails, and including the empty one for a data-only operation.

The reason is not tidiness. The command produces **three** artefacts: the migration, its
designer file, and the update to the **model snapshot**. The snapshot is what EF compares the
model against to generate **the next** migration. A hand-made scaffold leaves the three
inconsistent, and the damage shows up one migration later, in a file nobody is looking at.
**Compiling proves nothing about data being preserved.**

Remove the latest **unapplied** migration with `dotnet ef migrations remove`, never by deleting
its files. Find out where it was applied first: **a migration already in a shared environment
is preserved and corrected by a new one**, unless another strategy was agreed.

## Before generating

Identify the EF version, the provider, the `DbContext`, the target and startup projects and the
tooling that already exists. Read the intended change before generating anything.

**If manual editing is foreseeable — a rename, a data transformation, operations added to an
empty migration — say so before generating**: what will be edited, why, and how it will be
verified. **Generating does not authorise customising.** If the need only becomes visible in
the output, stop there and propose the same thing before touching the file. A confirmation
covers that exact intervention; it is not asked again unless the intervention changes.

After it is agreed, customise `Up` and `Down` as agreed, and review the provider-specific SQL,
the preservation of existing data and the reversibility. **If the original data cannot be
reconstructed, say so and say what the recovery is** — a rollback that pretends to work is
worse than none.

## If the command does not run, the migration is not written

The causes are few: the EF tooling is not installed, the project does not build, there is no
design-time factory or startup the tool can use, or it has no connection string to read.

Fix what is inside the authorised scope. **None of them is a reason to write one by hand.** If
generation stays blocked, report the command, its failure and what is missing — and **do not
report the migration as done.**

## Generating and applying are two different things

Generating or customising a migration **does not authorise applying it**. `dotnet ef database
update` is not run as a consequence, and `Database.Migrate()` is not added to startup.

- A **local or disposable** database can be used to verify the migration; that is covered by the
  plan, like any local environment.
- **A shared environment is not.** Applying there names the environment and belongs to
  `nzt-ship-release`, together with how migrations are packaged for deployment. **An unknown
  connection string is not assumed to be local.**

## Naming and granularity

- **The name says what changed**, in the code's language and in PascalCase:
  `AddCustomerTaxId`, `RenameOrderStatusColumn`. Not a date, not a ticket number, not `Update1`.
- **One migration per coherent change.** Two unrelated changes in one cannot be undone
  separately.
- If the model changed again **before the migration was ever applied**, remove it and generate
  it again. Two migrations that cancel each other are noise in the history forever.

## Read what came out before accepting it

The command is trusted to be consistent, not to be right about intent. Open the file and look
for the two things that are expensive to discover later:

- **Drops.** A `DropColumn` or `DropTable` nobody asked for means the model lost something by
  accident — usually a property that was renamed.
- **A rename that came out as drop + add.** EF cannot tell a rename from a deletion plus a
  creation, and when it guesses wrong **the data in that column is gone the day it is applied.**
  Propose `RenameColumn` instead, and confirm that edit before making it.

**Unexpected destructive output is reported, not applied while the decision is pending.**

Build the affected project, inspect the generated SQL, and on an authorised disposable database
check representative data before and after, testing the reversal where it is supported.
**Report inspection, build and actual database execution separately**: if nothing was executed,
data preservation was not tested and the report says so.

## Closing checklist

- [ ] A concrete schema or data operation justifies this migration.
- [ ] Generated with `dotnet ef migrations add`, never written by hand, with version, provider,
      context and project options identified first.
- [ ] Manual editing was explained and confirmed **before** it happened, and what was written
      matches what was confirmed.
- [ ] A generation failure was resolved or reported as a blocker — never worked around.
- [ ] Applied history was preserved; removal used the tooling.
- [ ] Nothing was applied beyond a local or disposable database.
- [ ] Drops, renames-as-drop-add and reversal limits were reviewed and reported.
- [ ] The name describes one coherent change, and the evidence separates inspection, build and
      execution.
